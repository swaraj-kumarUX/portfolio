Case study · redBus / redPro

HubbleUI Design System

PARTICLES looked like a design system. Nothing in production actually used it. I rebuilt its color foundation from measured, provable drift — then migrated redPro's first real component onto it, found a shipped accessibility bug on the way, and built the tooling to stop the drift from ever coming back unwatched.

Objective

Rebuild PARTICLES' color foundation into something engineers and designers could actually trust — provably, not just aesthetically — then prove it by migrating a real, shipped component onto it. A token file that's well-organized on paper but disconnected from production doesn't help anyone. And a fix that only holds until the next deadline doesn't either — which is why this work ends in tooling, not just a cleaner file.

The problem

Three compounding issues

PARTICLES existed. It wasn't trustworthy.

01

The colors drifted

Pasted in over time from different sources rather than engineered. The brand blue wandered between 213° and 223° across its own scale — "blue-100" and "blue-500" weren't the same blue, just lighter and darker versions of visibly different ones.

02

Accessibility failed

Success, warning and error text — used constantly in a data-dense B2B tool — sat at 3.9–4.3:1 contrast. WCAG AA requires 4.5:1. Real users with low vision couldn't reliably read status messages.

03

Production wasn't even connected

The deeper discovery: live components — real buttons, badges, inputs on shipped screens — were bound to a third, older system with 151+ legacy variable names. PARTICLES was a well-organized file nothing in production depended on.

Process · 01

Audit before engineering

Rather than guessing at fixes, I audited every family's hue, saturation and lightness numerically — plotting each on a hue wheel to make drift visible instead of eyeballing hex codes. That turns "these colors look a bit off" into a provable finding: blue-800 sits at 2° hue while the rest of the family sits at 8–10° is a fixable fact. "This looks slightly wrong" is not.

Process · 02

Engineer the gray scale from scratch

Grays are the hardest-working color in any interface, and the most tolerant of getting quietly wrong. I rebuilt the neutral ramp from 12 scattered values into 9 engineered stops: a single locked 216° cool undertone to harmonize with the brand blue, and lightness steps that rise unevenly — 4 → 6 → 8 → 10 → 12 → 14 → 15 → 16% — rather than a flat progression, because human vision compresses differences in dark tones more than light ones. gray-0 stayed deliberately pure white, since true white is still needed for elevated surfaces and inverse text — a case where forcing perfect uniformity would have been the wrong call.

Process · 03

Lock hue — without erasing character

Every chromatic family got locked to one mathematically precise hue — no more drift lightest to darkest. But I prototyped a fully "normalized" version too, where every family shared identical saturation and evenly-stepped lightness, and rejected it.

The judgment call

The normalized version produced an acidic green, muddy dark ambers, and would have shifted the protected brand blue to a more saturated, less calm color. Hue consistency was worth enforcing everywhere; saturation and lightness needed to stay hand-tuned per family — that's what reads as designed rather than generated. Knowing which axis to standardize and which to leave alone was the real work here, not running a formula.

Process · 04

Fix accessibility as engineering, not polish

The three failing feedback colors each needed a specific, calculated darkening — not a guess. I computed exactly how far each needed to move to clear 4.5:1 against its real background, then applied the minimum change needed: 2–3% lightness, visually almost imperceptible, but the difference between passing and failing AA. I folded each fix directly into the color's primary token rather than adding parallel "-600" variants — keeping the system lean instead of accumulating near-duplicate tokens to patch one problem.

Process · 05

Migrating Buttons — and finding the real bug

With the token foundation solid, I migrated Buttons — the first of 28 components — off the legacy system. This is where the deeper value showed up.

While mapping Buttons' legacy variables to PARTICLES tokens, I found a real, shipped accessibility bug: the button's Disabled + Hover state rendered white text on a light gray background — essentially invisible. Tracing why revealed the actual root cause: Disabled had been modeled as a value inside the button's color-intent axis, alongside "Active" and "Destructive" — which meant it got crossed against every hover and pressed state, combinations that should never have existed, since a disabled element can't be meaningfully hovered.

Symptom vs. defect

The fix wasn't just correcting that one instance of white-on-gray text — it was restructuring the variant architecture so Disabled became a state, orthogonal to color intent, matching how Material Design and Adobe Spectrum model it. That single structural change made the entire bug class structurally impossible to reintroduce, rather than patched once.

The same pass caught that "Tertiary" — meant to be the lowest-emphasis button style — was visually almost identical to "Secondary," both bordered and opaque. I made Tertiary borderless and transparent at rest, consistent with how text buttons work industry-wide, giving designers an actual third tier of emphasis instead of two options that looked the same.

Process · 06

Building the process, not just the fix

Migrating one component well is useful once. I built infrastructure to do it repeatably: a standardized 5-section documentation template per component — Use When · Do Not Use · Variant Map · Token List · Anti-Substitutions — where that last section explicitly encodes mistakes already found, so they can't quietly recur. Plus a running backlog capturing every deferred decision, so nothing gets silently dropped as the migration continues across the remaining 27 components.

The real work was learning which inconsistencies were bugs, and which were legitimate design decisions dressed up as inconsistencies.

Uniform hue was a bug. Uniform saturation across five different families was not — enforcing it anyway would have made the system worse while looking more "consistent" on paper.

The component migration reinforced the same lesson structurally: the visible symptom (invisible text) and the actual defect (a badly-modeled variant axis) were two different things. Fixing only the symptom would have left the system able to produce the same failure the next time someone added a state. Fixing the axis meant it couldn't.

A rebuilt, correct system still drifts the moment nobody's watching. So I built the thing that watches.

Why the fix couldn't end at component 1 of 28
Act two · the tool

HubbleUI Design Assistant

Auditing 27 more components by hand doesn't scale, and neither does trusting every future PR to remember the fixes above. So I designed and built a Figma plugin myself — ES5-compatible JavaScript running inside Figma's plugin sandbox, with its own UI, its own scoring logic, and a direct connection to Claude for the one check that needs a real eye. Four features, each closing a different way drift actually happens:

01

Audit + auto-fix

Scans fills, strokes, radius, spacing and type against the token scale. Off-system values get a severity, a plain-language reason, and the nearest token — found by colour-distance matching, not a guess.

02

Adoption Score

One number, five weighted dimensions: component coverage, token coverage, detachment, variant configuration, naming. Turns "is this on-system?" into something a lead can track over time.

03

Detached Instance Detector

Finds three distinct kinds of drift: fully detached layers rebuilt from scratch, broken links to a deleted component, and instances still linked but overridden — each override tagged token-bound or uncontrolled.

04

DAT — AI fidelity check

Upload a developer-build screenshot next to the Figma design; Claude compares them across colour, type, spacing, components and layout, and returns a scored, structured report.

Systems thinking

Turning "on-system?" into a number

A pass/fail audit tells you what's wrong on one frame. It doesn't tell a design lead whether adoption is improving file over file. The Adoption Score is a heuristic I designed to answer that — five dimensions, weighted by how much each actually signals real adoption rather than surface compliance:

  • Component coverage (35%) — the largest weight, because using real components is the strongest signal of adoption.
  • Token coverage (30%) — style checks that resolve to a token.
  • Detachment, inverse (15%) — penalises frames named like a component that aren't actually linked to one.
  • Variant configuration (10%) — instances with explicit component properties set, not left default.
  • Naming compliance (10%) — smallest weight deliberately: naming matters for handoff, but it's cosmetic next to whether the system is actually being used.
Drift detection

The drift an audit alone can't see

Off-token values are the obvious failure mode. The quieter one: a component instance still technically "linked" to CLUSTERS but locally overridden — a fill swapped, a radius nudged — looking compliant in a file search while it's silently forked from the system. The Detector separates that from full detachment (no link at all) and broken links (the source component is gone), and tags every override as either token-bound or uncontrolled.

AI review

Writing the rubric, not just calling the API

The DAT check sends both images to Claude with a fixed rubric — I wrote this prompt to force structured, comparable output every time, instead of a free-text opinion that reads differently on every run.

DAT reviewer prompt
You are a Design Acceptance Test (DAT) reviewer. The FIRST image is
the DEVELOPER-built screen. The SECOND image is the FIGMA DESIGN
(source of truth).

Compare them and identify visual mismatches across: colours,
typography, spacing, component usage, icons, layout/alignment,
and missing elements.

Respond ONLY with a valid JSON object — no markdown, no backticks:
{"summary":{"total":N,"critical":N,"major":N,"minor":N,"score":N},
 "issues":[{"id":N,"title":"...","severity":"critical|major|minor",
 "category":"colour|typography|spacing|component|icon|layout|missing",
 "description":"what is wrong","fix":"what the dev should change"}]}

Score is 0-100 (100 = pixel perfect). Be specific and actionable.
Reflection

What I caught in my own tool

The first version of the Audit only checked whether a value matched a token — a fill that happened to be #315ED1 passed, whether or not it was bound to the brand/primary variable. The moment the token changes, an unbound-but-matching value doesn't follow it, and silently drifts.

Fixing it meant reading Figma's Variables API properly — getBoundVarName() checks whether a property is genuinely linked to a live variable, not just numerically equal to one right now. It's a small function, and it's the difference between a checker that looks rigorous and one that actually is.

Outcome

A corrected foundation, enforced at the source

PARTICLES' color foundation is rebuilt and measured, not eyeballed. Buttons — component 1 of 28 — is fully migrated, documented, and carries a fixed accessibility bug the old architecture could never have surfaced by inspection alone. And HubbleUI Design Assistant is live and in active use across redPro design work, grown from a 263-line v3 that could only flag and auto-fix, into a 722-line v5 that scores adoption, classifies drift into three failure modes, and runs an AI fidelity check against real builds. Next: Badges, then the remaining 26 components, and the parked question of several hundred canvas elements still depending on deprecated legacy collections.

What's next

Designing with the system, not just checking against it

Plan — not yet built

Everything above catches drift after a designer has already made something. The next step goes earlier: give an agent the system itself — tokens, components, rules, patterns — as structured knowledge, so it can propose correct designs in the first place instead of getting audited afterward. Three layers, in order.

01

Knowledge — the design system, machine-readable

The same system this case study is about, rewritten as structured files an agent can actually read — not prose documentation, data. Tokens follow the identical Primitive → Semantic → Component chain built for color, extended to every token type. Component registry.md extends the same five-section template (Use-when, Do-not-use, Variant map, Anti-substitutions) built for the Buttons migration. A live Figma MCP feed keeps it current against the real file, not a snapshot.

Tokens.json — color typography spacing radius elevation unit values Component registry.md Design rules.md redPro patterns.md Icon library.md Figma MCP — live feed
02

Agent — Claude, with the system as its context

All seven knowledge sources compile into one agent-system-prompt.md: a persona, references back into the knowledge layer, output-format rules, an explicit decision sequence, and — the part that actually matters — guardrails. The guardrails are where "don't hardcode a hex" and "Disabled is a state, not a color intent" stop being rules a reviewer enforces after the fact, and become constraints the agent can't reason its way around while generating.

03

Execution — output, gated by approval

The agent proposes a plan first; it doesn't act unprompted. Only once that plan is approved does execution produce Figma frames, an HTML mockup, and a written design spec together, from the same source of truth, in one pass. The approval gate is deliberate — the same instinct behind building tooling that flags drift rather than silently auto-correcting it everywhere: a human stays the last check before anything reaches production.
